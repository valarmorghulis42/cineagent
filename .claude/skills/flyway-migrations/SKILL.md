# Flyway migrations — CineAgent

`ddl-auto=validate` is set project-wide (see `AGENTS.md` §2) — Hibernate never creates or alters
schema. Every table, column, constraint, and index is created by a Flyway migration under
`src/main/resources/db/migration/`. This skill is the checklist for writing one.

## The hard constraint: one migration set, two engines

The runtime default is H2 in PostgreSQL compatibility mode; the concurrency test suite additionally
runs the same migrations against real Postgres (via `zonky` embedded-postgres). **A migration that
only works on one of the two is a bug.** Concretely:

| Use this | Not this | Why |
|---|---|---|
| `BIGINT GENERATED BY DEFAULT AS IDENTITY` | `BIGSERIAL` | `BIGSERIAL` is Postgres-only syntax |
| `VARCHAR(n) ... CHECK (col IN ('A','B'))` | `CREATE TYPE ... AS ENUM` | Native enum types aren't portable, and are painful to alter later |
| `NUMERIC(12,2)` | `DECIMAL`/`MONEY`/float types | `NUMERIC` is exact and portable; never store money as anything else |
| `TIMESTAMP WITH TIME ZONE` | `TIMESTAMP`, `DATE` for instants | Everything timestamped is UTC `Instant` — see `AGENTS.md` §4.1 |
| A plain `UNIQUE (a, b)` | A **partial/conditional** unique index (`... WHERE status = 'ACTIVE'`) | H2 does not support partial indexes — this is *why* `show_seat` is modeled as one row per (show, seat) rather than one row per *active* hold |
| `TEXT` for any JSON payload (e.g. outbox) | `JSONB` | `JSONB` is Postgres-only; we never query inside the JSON anyway |
| `FOR UPDATE` on a **single table**, by primary key | `FOR UPDATE` joined across tables | H2 rejects `FOR UPDATE` combined with `JOIN` outright — see `AGENTS.md` §4.3 |

If a migration needs something not in this list, stop and check whether it's expressible in the
portable subset before reaching for an engine-specific feature — the portability requirement is a
deliberate scoping decision (no Docker available for the reviewer), not an oversight.

## Numbering and naming

- `V<n>__snake_case_description.sql`, strictly increasing, no gaps needed but no reuse.
- Roughly one migration per feature slice as it's built (`V1__core_schema.sql` for
  identity/catalog, `V2__show_and_booking.sql`, `V3__pricing_and_refund.sql`,
  `V4__outbox_and_idempotency.sql` — adjust as slices actually land; the point is one migration
  per logical unit of schema, not one giant migration).
- Seed data ships as its own migration, not mixed into schema DDL:
  `V100__seed_roles_and_admin.sql` for roles/admin user, `V900__demo_data.sql` reserved for the
  `demo` profile only (excluded from the default `db/migration` location and pointed to via a
  profile-specific `spring.flyway.locations` override — do not let demo data apply on `default`
  or `test` profiles).

## The rule that matters most: never edit an applied migration

Once a migration has been committed (i.e., could plausibly have been "applied" by anyone running
the app — assume immediately after commit), it is immutable. Flyway checksums migrations; editing
one after it's been applied breaks every existing database and every reviewer's second run. If a
schema change is needed:

- **Before the migration is committed**: edit it freely.
- **After it's committed**: write a new migration (`ALTER TABLE ...`) that changes what's needed.
  Never go back and rewrite `V1`.

## Indexes — add them with the query that needs them, not speculatively

Every index in this codebase should be traceable to a specific query pattern named in a comment
above the `CREATE INDEX` statement, e.g.:

```sql
-- Seat map browse query: WHERE show_id = ? — the single hottest read in the system
CREATE INDEX idx_show_seat_show_status ON show_seat (show_id, status);

-- Sweeper's expired-hold finder: WHERE status = 'HELD' AND hold_expires_at <= ?
CREATE INDEX idx_show_seat_hold_expiry ON show_seat (status, hold_expires_at);
```

This is what makes the "documented index rationale" enhancement (see the architecture plan) a
five-minute add instead of an afterthought — write the comment when you write the index, not
later.

## Constraints carry the invariants, not just the Java code

Every uniqueness/business invariant that the Java layer relies on should also exist as a DB
constraint, so a bug in the Java layer fails loudly (a constraint violation, caught and mapped to
a `ProblemDetail`) instead of silently corrupting data. In particular:
`UNIQUE(show_id, seat_id)` on `show_seat`, `UNIQUE(booking_id, show_seat_id)` on `booking_seat`
(not `UNIQUE(show_seat_id)` — see `AGENTS.md`/architecture plan on why), `UNIQUE(booking_id)` on
both `payment` and `refund`, `UNIQUE(dedupe_key)` on `outbox_message`.
